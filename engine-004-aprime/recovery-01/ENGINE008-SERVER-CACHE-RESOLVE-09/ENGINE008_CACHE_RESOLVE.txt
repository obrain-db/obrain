MODEL_SHA256_MS=64832.7

  j'avais infere ~6-7 s depuis l'ecart entre runs, en refusant de la presenter
  comme une mesure. La mesure reelle est **64 832,7 ms (64,8 s)** -- **dix fois

    load_model: obrain model identity: instance=1
      sha256=1d7c9409ae7f2c7f6071c8ad32d2481f2c09da94fc2aec3f63a4d44777e2b937
      (64832.7 ms)
  L'identite est calculee **AU CHARGEMENT du modele, avant toute requete**, et
  liee a **CETTE instance** : `kv_model_instance_new()` invalide l'empreinte
  precedente, et `kv_model_sha256(path, token)` ne reutilise le cache que si le
  **jeton d'instance** ET le chemin correspondent. **Une nouvelle instance ne
  reutilise donc jamais aveuglement l'identite precedente.**
  Le hachage est effectue **HORS du verrou global du cache** : une operation de
  64,8 s ne bloque pas les autres threads.
  Le contrat de reutilisation est donc etabli -- **mais son effet n'a pas ete
  mesure sur une deuxieme requete**, faute d'experience aboutie.

=== 4. OBSERVATIONS CORRIGEES DEPUIS LES FAITS ===
OBSERVED_TOKEN_COUNTS_RECONCILED=YES
  **Les 6 IDs de COMPLETE-08 etaient REELS, et le compteur 32 m'a induit en
  erreur -- pas la collecte.** Lu dans la boucle de production :
    `while (t < n_generate) { if (tok == eos) break; ... }`
  `n_generate=32` est un **PLAFOND**, pas un nombre produit. La generation a
  fait 6 tokens puis a rencontre **EOS** : le texte `.\n</think>\n\nOK.` fait
  exactement 6 tokens ([13,198,248069,271,3793,13]) suivis de `<|im_end|>`.
  **§4 annoncait ce piege mot pour mot : « ne pas confondre MAX_NEW_TOKENS
  demande et nombre produit ».** J'ai ajoute des compteurs distincts :
  `selected_ids_count`, `emitted_ids_count`, `n_generate_requested`,
  `stop_reason` (renseigne desormais par `cur_stop`, positionne sur `EOS` ou
  laisse a `MAX_NEW_TOKENS`). Le second site d'emission (acceptation
  speculative) est instrumente lui aussi, alors qu'il ne l'etait pas.

OBSERVED_DECODE_POSITIONS_CORRECT=YES (corrige, non re-observe)
  **La formule `cur_pos + t` etait FAUSSE** : `cur_pos` avance deja, donc les
  positions sortaient avec un pas de 2 (59,61,63,65,67,69).
  Corrige en enregistrant **`cur_pos` seul** -- qui est EXACTEMENT la position
  du batch transmis a `llama_decode` (`gen_batch.pos[0] = cur_pos`), ce que §4
  demande precisement. **Corrige dans le code et instrumente, mais NON
  re-observe** puisque aucune requete n'a abouti : je declare la correction,
  pas une observation.
