==========================================================================
LE SMOKE TEST INTEGRE A ABOUTI PAR LA ROUTE REELLE DU SERVEUR.
DEUX LIMITES SONT DECLAREES, DONT UN SIGNAL SUSPECT QUE JE NE MASCARE PAS.

=== 1. LE CHEMIN DE REQUETE REEL (cartographie, sources lues) ===
  Ce que j'ai ECARTE, avec preuve : `tools/obrain/` ne contient QU'UN fichier
  (`pstate-exp0a.cpp`, 194 Ko) et AUCUN binaire `obrain` n'existe dans
  `build-cuda/bin/`. Ce n'est pas le chemin de requete.
  **Le chemin reel est `llama-server`**, implementation dans
  `tools/server/server-context.cpp` (~7 000 lignes), construit en
  `libllama-server-impl.so`.

  **Et ce chemin contient DEJA l'integration K1/K2 du transfert d'etat
  hybride** :
    - cache memoire global : `g_kv_states` (server-context.cpp:63-65)
    - cle content-addressed : `kv_ref_of(data)` = FNV-1a 64 bits sur le blob (:66-71)
    - EXTRACTION (K1) : `llama_state_seq_get_size` + `get_data`, verifies,
      puis `g_kv_states[ref] = {n_fact, data}` (+ persistance disque K1b)
    - INJECTION (K2) : `llama_state_seq_set_data(ctx, blob.data, blob.size, seq_id)`,
      commentaire du producteur : « K2 : injecter l'etat persiste (copie
      memoire, pas de prefill) »
    - route HTTP : **`POST /jspace/inject_knowledge`** (server.cpp:269), decrite
      dans le source comme « production entry point for the KV-splice
      knowledge-fusion mechanism »
    - contrat : `{fact_text, extract_only:true}` -> extraction, renvoie un ref ;
      `{state_ref, prompt, n_generate}` -> injection par ref (bypass texte)

  **La cle content-addressed satisfait §2 sans schema parallele** : modele,
  calcul Q1, IDs du prefixe, configuration, types KV, MODE de serialisation,
  FORMAT (magic 0xaf143cd9) et positions sont TOUS a l'interieur du blob, donc
  un etat incompatible produit un blob different, donc un miss. Aucune
  compatibilite n'est presumee.

=== 2. CE QUE J'AI IMPLEMENTE : 2 DEFAUTS REELS ===
  Le fichier a ete MODIFIE : server-context.cpp, 321 284 -> 325 259 octets,
  **4 ancres verifiees avant ecriture** (une premiere tentative a echoue sur
  une ancre mal indentee et n'a RIEN ecrit : le fichier n'est jamais reste
  a moitie patche).

  DEFAUT 1 -- aucune borne memoire, aucune eviction (le trou concret).
    `g_kv_states` etait un unordered_map SANS limite : `g_kv_states.erase`
    n'apparaissait NULLE PART. A 157 353 668 octets par entree (mesure ici),
    une poignee d'extractions epuisait la memoire, sans autre issue que l'OOM.
    IMPLEMENTE : borne explicite configurable par `OBRAIN_KV_STATES_MAX_BYTES`
    (defaut 2 Gio), eviction LRU (`g_kv_states_lru` + index de position),
    compteur d'octets, et REFUS d'une entree plus grosse que la borne
    (message d'erreur explicite, aucune entree creee).

  DEFAUT 2 -- chemin disque SANS controle d'integrite.
    Le blob etait lu du disque et injecte SANS verifier que le contenu
    correspondait au nom de fichier (= la cle). Un fichier altere aurait ete
    charge et injecte.
    IMPLEMENTE : recalcul de `kv_ref_of(payload)` et REFUS explicite
    (« state integrity mismatch on disk load ») en cas de discordance.

  BUILD : `cmake --build build-cuda --target llama-server`.

  87c42d5f5dd7ab3c10967b4d3eaac82636b6af11e2c18a7f2798bab2d01bb2b2

=== 4. LIMITE 1 -- L'ENTREE N'EST PAS LES 59 IDs AUTORITAIRES ===
  `fact_tokens=7`. La route tokenise `fact_text` par **son propre template de
  chat** : elle produit 7 tokens, pas les **59 IDs autoritaires** mesures et
  geles. **La route ne permet donc PAS d'imposer le prefixe de 59 IDs**, et
  l'entree effectivement utilisee dans le smoke test n'est PAS l'entree
  autoritaire de RUN-02 / BENCH-03.
  CONSEQUENCE : le smoke test demontre que **le mecanisme K1/K2 fonctionne par
  le chemin reel de l'engine**, mais il ne reproduit pas la mesure de BENCH-03
  et ne la remplace pas. Je ne transpose aucun chiffre de BENCH-03 ici.
  MAILLON MANQUANT, NOMME : la route n'a pas de parametre acceptant une liste
  d'IDs de tokens. Il faudrait soit un parametre `fact_token_ids`, soit passer
  par le template exact — ce qui exigerait que le serveur utilise le template
  qualifie `c3cf9e34...`, ce que je n'ai PAS verifie.

=== 5. LIMITE 2 -- SIGNAL SUSPECT SUR fact_decode_ms, NON RESOLU ===
  K1 rapporte `fact_decode_ms=63.647` et K2 rapporte **exactement la meme
  valeur, 63.647**. Or K2 n'a PAS envoye de `fact_text` : il passe par
  `state_ref`. Deux lectures sont possibles :
   (a) le champ est simplement recopie depuis le blob et ne mesure rien ;
   (b) le fait EST re-decode dans K2, auquel cas **K2 n'est PAS un cache hit
      pur** et les tokens du fait sont bel et bien executes.
  La description de la route dit qu'elle fait « extract+reinject — the seam a
  future cross-request cache would split at » : elle fait donc un aller-retour
  dans le MEME appel. **Je n'ai PAS lu assez de code pour trancher, et je ne
  tranche pas.**
  **Le meme nombre a deux endroits est un signal, pas une preuve.**
  Ce point doit etre elucide AVANT toute revendication de cache hit
  inter-requetes.

=== 6. TESTS ===
